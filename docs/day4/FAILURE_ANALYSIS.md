## A. Failures of the system

### A1. Wrong company reported as the vendor

- **What happened.** When the extractor returned the printed "Bill To" customer (or the "Remit to" bank name) as the vendor, the system approved the invoice, or missed a duplicate. In the worst case an exact duplicate (TC05) was approved.
- **How it was found.** Fault F05 on documents that print a customer block; later the held-out fault H04.
- **Why nothing caught it.** The grounding check only asks "does this string appear in the document?" and a customer name does. No rule compared the invoice's vendor with the PO's vendor, and the duplicate check looked up the log using the extracted vendor only, so a wrong vendor silently hid a duplicate.
- **Root cause.** The design verified that a value *exists* in the document but never that it was the *right kind of value*, and the extracted vendor was trusted as the only key.
- **Fix.** (1) New finding `VENDOR_MISMATCH`: the invoice's vendor must match the PO's vendor, tolerating legal suffixes (Ltd, Limited, Inc, GmbH) but not look-alikes (similarity threshold 0.95, chosen deliberately because look-alike vendor names are a known fraud pattern). (2) The duplicate check now compares against the extracted vendor **and** the PO's vendor. (3) No vendor email is drafted when the vendor is in doubt.
- **Regression tests.** `test_vendor_not_matching_po_is_flagged_and_blocks_the_vendor_email`, `test_duplicate_is_still_found_when_the_extracted_vendor_is_wrong`, the look-alike and suffix tests, and the whole-matrix gates.
- **Evidence it matters.** In the ablation, removing this check makes F05 and H04 unsafe again (3 + 3 runs).
- **Residual risk.** When an invoice has no PO number or an unknown PO (TC07, TC08) the vendor cannot be cross-checked. A legitimate invoice from a subcontractor or a differently named entity will be sent to review.

### A2. The PO number reported as the invoice number

- **What happened.** 9 clean-invoice runs were approved with the wrong invoice number. For the duplicate case the system was saved only by accident: a second, unrelated rule (same vendor, total and date) happened to fire and downgraded Reject to Review.
- **How it was found.** Fault F06.
- **Root cause.** Same family as A1: the PO number is printed on the invoice, so it passes grounding. Nothing knew that the invoice number and the PO number are different kinds of identifier.
- **Fix.** A cross-field check: an invoice number equal to the PO number is rejected and the model is asked once to correct it. Round 2's label anchoring (A3, A4) later made this check redundant on the test set (see the ablation), and it is kept as cheap redundancy.
- **Regression test.** `test_invoice_number_equal_to_po_number_is_rejected`.

### A3. Another printed date reported as the invoice date

- **What happened.** The due date, delivery date or order date, reported as the invoice date, was accepted. This matters because the *possible duplicate* rule depends on the date, so the wrong date let a probable duplicate (TC06) through as Approve.
- **How it was found.** F10 (due date), then the held-out faults H01 (delivery date) and H02 (order date).
- **Round 1 fix did not generalize.** I added a check that rejects a date printed only after the word "due". That fixed F10 completely, and on the held-out set **11 unsafe runs remained**, because delivery and order dates are not preceded by "due". This is the most important lesson of the day: a fix designed against the faults I had already seen was too narrow, and only held-out faults showed it.
- **Root cause.** The same as A1 and A2, stated more generally: *the system confirmed that a value was in the document, not that it was next to the right label.*
- **Fix (round 2).** Label anchoring (`ap/anchors.py`): the invoice date must sit next to an invoice-date label ("Invoice Date", "Issued", "Date" not preceded by due, delivery, order, ship, payment and similar words). The same mechanism covers the invoice number and the total. A check applies only when the document has at least one label of that kind; with unfamiliar wording it is skipped rather than guessed.
- **Evidence.** Held-out unsafe runs: 11, then 0. Ablation: removing anchoring brings back exactly H01, H02 and H03 (11 runs) and nothing else.
- **Regression tests.** `test_other_printed_dates_are_rejected_by_label_anchoring`, `test_date_anchoring_ignores_due_delivery_and_order_dates`, and the held-out gate.
- **Residual risk.** Documents whose labels are unfamiliar ("Rechnungsdatum", "Dated this day") get no anchoring. A date or number printed *in the wrong place beside a correct-looking label* is not detectable by this mechanism.

### A4. The customer's own reference reported as the invoice number

- **What happened.** 3 clean runs approved with the customer's order reference ("Your ref: ORD-5505") as the invoice number.
- **How it was found.** Held-out fault H03. Round 1 did not catch it.
- **Root cause and fix.** Same as A3: anchoring requires the invoice number to follow a label such as "Invoice No", "Bill No" or "Invoice #", and requires a whole-token match, so a prefix (`INV-50` vs `INV-5001`) cannot pass.
- **Regression tests.** `test_customer_reference_as_invoice_number_is_rejected`, `test_invoice_number_must_match_whole_token_not_a_prefix`, `test_invoice_number_labels_across_layouts`.

### A5. European number format

- **What happened.** With a **perfect** extractor (so no model involved), all 12 European-format invoices (`47.500,00`) were rejected as unreadable. Three clean invoices were wrongly flagged and one exact duplicate was downgraded from Reject to Review. The other eight happened to receive the right *label* only because they are exception cases that get flagged anyway, with the wrong *reason*.
- **How it was found.** The robustness set (document variants with ground truth held constant).
- **Root cause.** The number reader in the grounding check assumed US format (`1,234.56`), so the printed total never matched the extracted total.
- **Fix.** Every printed number is read in both conventions; ambiguous tokens such as `1.234` yield both readings. Date forms with dots (`05.11.2026`) were already handled.
- **Trade-off, stated plainly.** Accepting both readings makes grounding slightly more permissive (a value can be "found" through the other convention). It cannot make an unrelated number match, and anchoring and arithmetic still apply.
- **Regression tests.** `test_number_readings_cover_both_conventions`, `test_european_invoice_total_is_grounded`, the perfect-extractor gate over all 60 documents.

### A6. Harmless packaging quirks caused avoidable reviews

- **What happened.** 36 false alarms: a correct answer wrapped in a markdown code fence (F11), amounts returned as `"47,500.00"` strings (F12), and slightly reworded item descriptions (F17) each sent 12 clean invoices to review.
- **Root cause.** Strict parsing with no tolerance for format-only variation. With a provider that does not enforce a schema (a local model, for example) this would have meant most invoices going to review.
- **Fix.** Code fences are stripped (and recorded in `repairs`); US-style numeric strings are accepted; descriptions are grounded word by word with plurals tolerated; near-identical line names match a PO line **only if their digits are identical**, so `desk 120 cm` is never matched to `desk 160 cm`. Ambiguous strings (`"1.234,56"`) are still rejected rather than guessed.
- **Regression tests.** The format-tolerance tests and `test_near_duplicate_line_names_match_but_different_products_never_do`. A mutation test showed my first version of that test did not actually protect the digit guard; the test was strengthened (see section B).

### A7. A subtotal accepted as the total (caught before it shipped)

- **What happened.** While writing tests for anchoring, `Subtotal 100.00 Total 150.00` anchored the value 100 as the total. The anchoring look-behind also read the words *before* the "Total" label.
- **Why it matters.** Invoices with tax lines print subtotal, tax, then total. A model that reports the subtotal as the total passes arithmetic (lines sum to the subtotal) and grounding.
- **Fix.** The value must follow the label; the words before it are consulted only when nothing numeric follows.
- **Regression tests.** `test_total_is_found_after_or_before_its_label_and_subtotal_is_ignored`, `test_subtotal_reported_as_total_is_caught_by_anchoring`. Invoices with tax lines are a documented non-goal; the test `test_invoice_with_tax_and_correct_total_is_sent_to_review_not_approved` confirms they fail **safe** (sent to review) rather than silently.

## B. What each safeguard is for (ablation)

Switching off one safeguard at a time and re-running 802 simulated-fault runs:

| Safeguard removed | Unsafe runs (main / held-out) | Faults that get through |
|---|---|---|
| none (everything on) | 0 / 0 | |
| Grounding in the document text | 8 / 0 | F07 hallucinated PO, F09 flipped currency |
| Arithmetic (lines, sum) | 4 / 0 | F02 total copied from a line |
| Label anchoring | 0 / 11 | H01, H02, H03 |
| Vendor-vs-PO check | 3 / 3 | F05, H04 |
| Cross-field checks (invoice no = PO, due date) | 0 / 0 | none: redundant on this test set |
| Confidence gate (retry or low confidence goes to a human) | 0 / 0 | none: not needed on this test set |

Two honest conclusions: each of the four main layers has a distinct job and none can be removed; and **two layers show no unique contribution on this data** (the cross-field checks, now backed by anchoring, and the confidence gate). They are kept as cheap redundancy, but I cannot claim this evidence proves they are necessary.
